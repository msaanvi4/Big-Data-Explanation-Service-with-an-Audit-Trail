# Loan Decision Audit Storage Design

**Person 1 deliverable** — Iceberg table schema, partitioning rationale, sample structure, and lineage.

## 1. Design decision

Store each demonstration prediction as an immutable audit event linked to the exact minimized input snapshot, explanation payload, and immutable model build. Use Apache Iceberg tables backed by Parquet with Zstandard compression, time based partitioning, and retained snapshots so a past decision can be retrieved and replayed.

## 2. Dataset and privacy boundary

The assignment suggests Home Credit Default Risk, while the supplied project CSV is the Lending Club loan granting dataset. The Zenodo source record reports 1,347,681 records; the local CSV has 15 columns. Its `Default` label represents final repayment status (fully paid versus default), not an original accept/deny outcome. Any decisions generated by this project must be labelled demonstration decisions.

The source describes borrower-level financial, employment, housing, state, ZIP, and free-text fields. Since the course brief prohibits real personal data, use synthetic loan applications for implementation and examples. Do not ingest or redistribute the supplied CSV without instructor confirmation. In all cases, exclude `title`, `desc`, raw ZIP, and source loan IDs from the model and audit payload. Do not retain a customer ID in the audit tables.

## 3. Logical architecture and ERD

```text
Synthetic application -> versioned feature transform -> versioned model + explainer
                                                       | prediction event
                                                       v
model_registry 1 --- * prediction_events * --- 1 input_snapshots
                                 |
                                 1
                                 |
                         explanation_records

Iceberg tables -> Parquet + ZSTD -> object storage + retained snapshot metadata
```

`prediction_events` is the audit anchor. UUID links connect the exact prediction, input snapshot, explanation and model. Iceberg does not enforce uniqueness or foreign keys; validate them in the write pipeline.

## 4. Table contracts

### `prediction_events` — one row per scoring call

| Field | Type | Contract |
|---|---|---|
| `prediction_id` | string / UUID | Required, unique, generated per request |
| `decision_ts` | timestamp(6), UTC | Required event time |
| `decision_date` | date | Derived from `decision_ts`; partition convenience |
| `demo_decision` | string enum | `APPROVE`, `REVIEW`, or `DECLINE` under a documented demo threshold |
| `risk_score` | double | Finite value in [0,1]; document score semantics |
| `model_version` | string | Exact immutable model build key |
| `input_snapshot_id` | string / UUID | Exact model input record |
| `explanation_id` | string / UUID | Exact explanation record |
| `request_trace_id` | string | Synthetic tracing token, not a real customer key |
| `schema_version` | string | Contract version, e.g. `1.0.0` |

### `input_snapshots` — one row per prediction

Store canonical post-transform values actually supplied to the model. `Default` is a training label only and is never part of inference input.

| Field | Type | Contract |
|---|---|---|
| `input_snapshot_id` | string / UUID | Unique immutable snapshot ID |
| `prediction_id` | string / UUID | Required link to event |
| `feature_schema_version` | string | Ordered model-input contract version |
| `loan_amnt`, `revenue` | decimal(12,2) | Synthetic values; nonnegative |
| `dti_n` | decimal(7,4) | Synthetic debt-to-income value; validate range |
| `fico_n` | int | Synthetic score; validate 300–850 if modeled |
| `experience_c` | boolean | Normalize source binary encoding |
| `emp_length`, `purpose`, `home_ownership_n` | string | Normalized, allowlisted categories |
| `input_hash` | string SHA-256 | Hash canonical sorted JSON of model inputs |
| `created_at` | timestamp UTC | Snapshot creation time |

### `explanation_records` — one row per prediction

| Field | Type | Contract |
|---|---|---|
| `explanation_id` | string / UUID | Unique explanation artifact ID |
| `prediction_id` | string / UUID | Required link to event |
| `explainer_name`, `explainer_version` | string | Method and exact implementation version |
| `explanation_json` | struct / JSON | Ranked contributions with feature, contribution, and direction |
| `reason_codes` | array<string> | Stable vocabulary with its version recorded |
| `rendered_summary` | string | Versioned template output; no untrusted borrower text |
| `explanation_hash` | string SHA-256 | Hash canonical explanation and rendering inputs |
| `created_at` | timestamp UTC | Explanation generation time |

### `model_registry` — one row per immutable model build

Store `model_version`, artifact URI and SHA-256 digest, framework/runtime version, feature-code commit, preprocessing artifact digest, training dataset identifier/version/hash and window, label definition, threshold-policy version, explainer compatibility, and registration time. Keep binaries in immutable object storage; Iceberg holds metadata and digests.

## 5. Partitioning, format, and compression

- Use Iceberg v2 with Parquet. Start with Zstandard compression level 3; benchmark against Snappy on the synthetic workload.
- Partition events by `days(decision_ts)` and child tables by `days(created_at)` set at scoring time. This keeps related records in the matching daily partition for date-bounded queries. For a small class demo, use `months(decision_ts)` and corresponding month transforms on child timestamps if daily partitions are too sparse.
- Sort by `prediction_id` and consider write distribution by `decision_date`. Avoid partitions on applicant ID or any high-cardinality/sensitive field.
- Compact data files to a target of 256–512 MiB after write bursts. Tune for engine and object store; do not create one file per prediction.
- Preserve Iceberg metadata and snapshots for the declared audit window. Do not expire snapshots needed by the reproducibility test.

## 6. Time travel and reproducibility

1. Append audit records; corrections create new records with an optional `supersedes_prediction_id` rather than overwriting history.
2. Write event, input, and explanation rows as one logical batch with stable IDs. Detect partial commits and orphan links.
3. Record the Iceberg snapshot ID or commit timestamp in a run manifest.
4. Pin the model binary, preprocessing code, explainer, feature schema, reason-code map, and threshold policy by version or digest.
5. At replay time, read the exact row at the recorded Iceberg snapshot, verify input and explanation hashes, rerun the pinned model, then compare score within a declared numeric tolerance and decision exactly.
6. Set snapshot expiration and orphan cleanup beyond the agreed audit retention period; retain all snapshots through project evaluation.

## 7. Historical query interface

```sql
SELECT p.prediction_id, p.decision_ts, p.demo_decision, p.risk_score,
       p.model_version, i.input_hash, e.explainer_name,
       e.explainer_version, e.reason_codes, e.explanation_json
FROM audit.prediction_events p
JOIN audit.input_snapshots i USING (input_snapshot_id)
JOIN audit.explanation_records e USING (explanation_id)
WHERE p.prediction_id = :prediction_id;
```

Filter by prediction ID first and return only the decision, score, model version, explanation, and input hash by default. Raw feature values require an authorized audit role. Person 2 should measure p50/p95 latency, bytes scanned, and rows returned over increasing synthetic volumes. The design alone does not prove seconds-level response time.

## 8. Lineage and governance

```text
synthetic generator + seed/version
 -> feature contract version
 -> model digest + preprocessing code commit
 -> prediction + threshold-policy version
 -> explainer version + reason-code map
 -> Iceberg snapshot ID + Parquet metadata
```

Record dataset source, version, license, access date, checksum, and transformations in the project data card. The Zenodo record describes source fields and target semantics; its rights area did not visibly state a license during inspection. Verify the terms before redistribution.

## 9. Acceptance checks

- Every event resolves to exactly one input, explanation, and model build; duplicate/orphan checks run at write time.
- Hash verification reproduces the stored canonical input and explanation hashes.
- A time-travel query at the recorded Iceberg snapshot returns the original row after later appends or schema changes.
- Pinned model and preprocessing reproduce the score within a declared tolerance and reproduce the decision exactly.
- A synthetic fixture proves the lookup response excludes direct identifiers and free text; performance measurements are reported by Person 2.
